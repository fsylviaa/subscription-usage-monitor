## 每次开始前必读

1. 先读 [项目进度](docs/项目进度.md)：当前任务、上次停点、待验/受阻事项和建议下一项。
2. 读 [任务总览](docs/mvp任务清单/README.md)、本次任务文件及其直接前置的状态/验收记录，并读 [执行约定](docs/mvp任务清单/执行约定.md)。核对当前 Git 变更与相关提交，不能只凭看板文字判断前置完成。
3. 按需读取 [需求正文](docs/requirements.md)、[决定记录](docs/decisions.md)、[技术方案](docs/首版平台登录与额度连接方案.md) 对应章节。最新明确用户指令优先；历史方案或原型不扩大范围。
4. 确认本次只交付一个小成果；简短说明要做什么及用户怎样验收。缺少前置时说明缺项，不绕过依赖或擅自改做另一任务。
5. 实际开始修改时，将该任务在看板及任务文件中标为进行中。只读查询不为了更新时间而制造进度变更。发现上次中断或记录与文件不一致，先依据真实文件、验收证据和 Git 历史修正交接信息，保留未知项，不臆测完成。

## 每次交付前必须更新

完成一个小功能、任何修改或修复、收到验收结果，以及正常结束但尚未完成任务时，都由执行者主动完成以下步骤：

1. 更新 [项目进度](docs/项目进度.md) 的当前概况、对应任务行和本次交接：实际做了什么、检查结果、还没做什么、待验或阻碍、下一步建议。进度只记事实，不把计划写成成果。
2. 同步任务文件状态，并创建或追加 `docs/mvp任务清单/记录/Txx-验收.md`。逐条保留操作/输入、预期、实际结果和真实/测试环境区别。后续修复及用户反馈按日期追加，不能抹掉先前失败记录。
3. 小修复沿用原任务编号并记录本次差异。若独立改动确实超出原小任务，按执行约定拆出有范围、依赖和验收的新任务，加入总览与看板。项目规则或规划维护可记为“项目维护”，不伪装成完成 T01 等开发任务。
4. 只暂存本次成果、相关任务/验收记录和进度文档，一起建立 Git 存档点；保护其他未提交工作。提交说明含任务编号；项目维护使用明确的文档提交说明。用户未要求时不推送远端。
5. 提交成功后核对真实提交号和剩余变更，向用户报告“做了什么、怎么验收、实际结果、待验事项、进度已更新、提交号”。文档不填写本次提交自身哈希；通过任务编号/准确提交说明定位，后续记录可引用已存在的哈希。

**缺少进度更新或 Git 存档，不能宣称本次任务已完整交付。** 若提交失败，文档和回复必须标注未存档，任务保持未完成；未完成的工作可提交阶段存档，不等于完成任务。意外中断后由下一次启动按真实状态补齐记录。

## 状态和验收

- 看板是统一进度入口；任务文件保存范围、依赖和状态摘要，验收记录保存证据。更新时三者一致，其他文档引用看板，不另建一套实时统计。
- 任务状态：未开始、进行中、待验、受阻、已完成、已取消。“已取消”只用于用户明确撤销的范围，不计作已完成，也不再作为后续前置。“待验”表示任务必要验证尚未齐；“已完成”必须满足本任务范围成果存在、必要验收通过、记录齐全且 Git 存档成功。
- 用户亲验单独记录：未亲验、部分通过、通过、未通过，附明确反馈来源。不能把开发者自检当成用户已验收。用户尚未亲验不自动成为所有后续任务的阻塞，仍以任务规定的必要验收和依赖为准。
- 用户报告真实缺陷时，重新评估受影响任务及后续依赖，恢复为进行中/待验/受阻并说明原因；不继续把已失效的通过结果当作当前结果。
- 自然后台调度、真实重置通知和授权续期未发生时如实待验；可以推进用户已授权且前置齐备的独立任务，不降低最终真机验收标准。
