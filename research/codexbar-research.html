CodexBar 很适合当作“各平台额度接入的参考库”，但不能直接打包成 iPhone App。值得借用的是平台请求、数据解释、账户隔离和错误处理；最需要重新设计的是登录、凭据保存、手机后台刷新，以及第三方服务对你这个新 App 的授权。

可以把它想成一个“替你向很多商家查会员余额的管家”。每家商店的会员卡、查账窗口和账单格式都不同，它为每家准备了一套办法，再把结果整理成你看得懂的进度条。

显示内容大白话解释需要注意
订阅额度会员包里的本轮、每周或每月额度用了多少，什么时候恢复。一个账户可能同时被好几条限额约束；不是把几条剩余额度相加。

登录是怎么切进去的

先把“你用什么方式证明自己是谁”和“软件拿什么凭据查额度”分开。Apple ID、Google、邮箱密码，是进入服务商账户的方法；登录成功后的 token、Cookie 或 API key，则像服务商发出的通行证。CodexBar 大多数时候接手的是通行证，不是 Apple 密码或邮箱密码。

这意味着：同一个平台账户，只要官方登录后给出了项目支持的凭据形式，最初用 Apple 还是邮箱通常不会改变查额度的基本逻辑。具体登录选项仍由平台决定。不要把“给我们的 App 加一个使用 Apple 登录按钮”误认为能自动获得用户的 OpenAI、Claude 或其他平台账户授权。

路径项目怎么做搬到手机时的含义
借用官方电脑工具Codex、Claude、Gemini 等从电脑工具留下的文件或钥匙串中取凭据；必要时启动该工具登录。iPhone 没有这些电脑目录和命令行工具，需要重新建立授权流程。
设备验证码授权Copilot 展示验证码、打开 GitHub 官网，让用户在那里确认；程序等待授权完成。交互可以借鉴，但要确认自己的应用身份能获得查询 Copilot 额度的权限。
借用网页登录状态Cursor、Manus、Notion 等读取特定网站的 Cookie 或浏览器存储；也提供手动导入。不能直接读取 iPhone Safari 或其他 App 的私人登录数据。自有网页登录也不保证获得可长期使用的查额凭据。
用户提供访问密钥DeepSeek、OpenRouter、ElevenLabs 等带用户密钥请求平台接口。网络请求通常较好迁移，但密钥权限、可查询数据和保存方式仍要逐项确认。
直接用户名密码StepFun 是明确例外：项目自己提交用户名密码，换取会话凭据。不要把这种做法推广到所有平台；现有密码保存方式也需要重做。

Codex 的完整例子

  1. 用户点登录后，项目启动官方 codex login，由官方工具完成浏览器登录。CodexBar 本地没有自己实现一整套 Apple 登录、PKCE 或网页登录回调。
  2. 官方工具留下 auth.json。里面可能包含访问凭据、续期凭据、账户标识、过期时间。CodexBar 按指定账户目录读取。
  3. 自动模式按 PAT → OAuth → CLI 尝试可用路径；指定工作区时会限制不带工作区范围的 CLI 回退，避免查错账户。
  4. OAuth 路径带访问凭据和账户标识，查询 chatgpt.com/backend-api/wham/usage。返回结果再整理为短周期、周限额、余额等。网页附加明细是另一条来源，不是有一个 token 就自然有所有账单。
  5. 凭据过期时，当前额度读取路径刻意不自行兑换共享的续期凭据。原生凭据在允许时交官方 CLI 恢复；外部凭据需回所属工具重新登录，指定工作区时也可能禁止 CLI 回退，不能保证自动续期。这是为了避免“手机和电脑同时续期，把对方手中的票据弄作废”。源码有刷新辅助类，不代表当前读取路径正在调用它。
  6. 多个 Codex 账户使用分别管理的目录，并核对用户和工作区。网页 Cookie、缓存和额度也要跟着账户分隔，不能只看显示邮箱就拼到一起。

PAT 是另一种工作区访问凭据，不能当作普通 OpenAI API key。项目先查询它属于谁，再查询那个账户的额度。截至本次核验，官方文档将 Codex 访问令牌支持范围列为 ChatGPT Business 和 Enterprise，因此不能把这条路径当成面向所有 Plus/Pro 用户的手机登录方案。官方访问令牌说明。

当前官方也已有 Sign in with ChatGPT 的相关集成文档：开源、本地应用有对应的计划使用授权流程，付费或远程托管场景另有申请渠道。这是新 App 可以调查的方向；这些文档本身没有证明我们的额度监控 App 已获得读取该内部额度接口的权限，不能直接套用官方工具的应用标识。官方集成范围、客户端申请说明。

其他平台的关键差异

  • Claude：区分官方工具凭据、手工 token、网页 Cookie 和管理 API key；这些能读到的内容不同。项目还记录“谁负责续期”，避免几个程序抢着换同一张票据。管理 API 的费用不等于个人订阅剩余额度。
  • Copilot：设备授权流程目前使用 VS Code 的应用标识。复制这段代码能发出请求，不代表新 App 可继续使用这个身份，也不代表自己的 GitHub 授权天然能读内部额度接口。
  • Gemini：读取已安装 Gemini CLI 的凭据，还会从其安装文件解析授权参数。不能原样搬到手机；个人、AI Pro、Ultra 的旧 CLI 登录路线还有迁移变化。
  • Cursor：既能借浏览器会话，也会读取电脑上 Cursor 自己的数据库。它不是只打开一个登录网页，就能在任意系统拿到同样数据。
  • StepFun：源码把用户名放入统一配置的 apiKey 字段，把密码放入 cookieHeader 字段。这个版本确实存在保存密码的路径，不能直接复述 README 的“不会保存密码”。

保存凭据也不是“全部存在钥匙串”。手动密钥、部分 token 和账户列表存在配置 JSON，依靠仅本人可读写的文件权限；部分自动 Cookie/OAuth 缓存使用钥匙串。对 iOS 新项目，建议普通数据库只保存“钥匙在哪里”的引用，真正的密钥放系统 Keychain。Apple Keychain 说明。

适合怎样借用到 iOS

最值得借的是“按平台分开接入、统一整理结果”的骨架。核心库还混有启动电脑程序、读浏览器目录、扫描进程等代码，因此不是给新 iOS 工程勾选一个依赖就能运行的现成 SDK。需要把这些桌面能力从纯网络与解析代码中拆出来。

复用判断具体内容
优先抽取数据格式、比例与时间解释、平台返回结果解析、账户和工作区隔离、查询失败分类、测试样本。对于可获授权的接口，抽取网络请求逻辑。
调整后使用刷新调度、图表、历史保存、小组件、插件运行环境；统一额度模型也应减少当前大量平台专用字段。
需要重做首次登录、续期责任、Keychain 保存、退出清理、iOS 页面、后台策略、自己的应用标识、CloudKit 容器和发布配置。
不能原样搬运读取其他 App 私人文件或钥匙串、导入电脑浏览器 Cookie、运行 Codex/Claude CLI、扫描桌面进程、Mac 菜单栏及 Sparkle 更新。

苹果对 iOS App 做了隔离：一个 App 不能随意读取另一个 App 的私人文件，只能走系统明确提供的渠道。因此“用户手机已装 ChatGPT 且已登录”，不代表我们的 App 能拿到它的登录状态。Apple 应用隔离说明。

有正式授权回调的平台，可以考虑系统网页登录组件 ASWebAuthenticationSession。它像“陪用户去官方柜台办授权，再拿回官方交给本 App 的回执”，不是让 App 偷看 Safari 的 Cookie。Apple 网页授权组件。

产品路线优点代价与适用情况
手机直接连接平台不要求电脑在线；密钥可以留在用户手机。适合明确开放访问密钥或授权接口的平台。首版平台数量应服从真实接入能力，不能先承诺 91 个。
手机 + 用户电脑采集端电脑继续利用已有登录状态，手机只看同步后的额度；复用范围通常更大。电脑需要运行；离线时只能显示最后一次结果。必须做配对、加密传输和断连提示，不适合作为“完全独立手机 App”的无条件替代。
自己的服务器集中查询便于集中调度、发送变化通知。要处理所有用户的凭据和隔离、费用、风控与服务授权；服务器也不能凭空解决没有查询权限的问题。

仓库已有可复用的“电脑给手机提供结果”基础。codexbar dashboard 能输出统一结果；codexbar serve 提供 /dashboard/v1/snapshot，包括平台、账户、额度、更新时间和错误。它不是现成手机服务：默认只监听本机，传输是普通 HTTP；跨设备使用需配对、身份校验和加密通道。现有 Dashboard 接口说明。

我的建议是先以独立手机使用为首版目标，挑出能明确授权、可长期续期的入口；把 Codex、Claude、Copilot、Cursor 作为单独的登录可行性验证。若这些订阅平台是产品不可缺少的核心，而纯手机授权无法成立，再决定是否接受电脑采集端。

可以采用“凭据保存在 iPhone Keychain、手机直接查询”的基础设计；不能把同一种网页登录流程套到全部 91 个入口。钥匙串负责保管已经拿到的通行证，平台决定是否发证、允许查什么、如何续期。界面上看起来都是“打开网页”，内部可能是不同的流程。

本节按你描述的竞品交互评估技术可行性，没有确认竞品的私有实现。仅凭“弹出网页、登录后保存到钥匙串”，无法判定它使用正式授权回调、自己的网页会话，还是其他平台专用方式。下面的手机方案属于基于源码的改造设计，尚未在真机和真实账户上验证。

  1. 正式授权：为我们的 App 申请平台支持的客户端身份，用系统网页授权窗口；标准原生 OAuth 采用授权码与 PKCE，验证回调及 state。它像“只有本次申请的人能兑换的取票码”。不能把桌面官方工具的身份或固定回调直接当作我们的身份，也不能把可保密的服务端密钥硬塞进 App。原生应用 OAuth 标准。
  2. 访问密钥：打开官方密钥管理页供用户创建，再由用户明确粘贴到 App；保存在 Keychain，选择最小可用权限。它不一定有“刷新令牌”，被撤销或到期通常由用户换新密钥。不能把 API 钱包当成个人会员额度。
  3. 网页会话：在平台允许且实测可行的前提下，用独立 WKWebView 登录；只提取该平台查询必需的会话，验证账户后保存。恢复 Cookie 时保留域、路径、安全标记和有效期；只发往对应平台允许的地址。localStorage、短期令牌、设备密钥须按平台单独处理。不能宣称把一个 Cookie 字符串写进 Keychain 就解决了登录。
  4. 凭据保管：以“平台 + 地区/服务器 + 稳定账户标识 + 工作区”隔离；OAuth 保存访问/续期凭据及到期时间，密钥路线保存 key，网页路线保存必要会话与绑定信息。普通配置与日志不存这些原文。这里的 Keychain 是 App 使用的系统秘密存储，不是让 App 读取用户“密码”应用中的所有账户。
  5. 额度更新：用 URLSession 抽取并调用已有查询逻辑。每个账户同一时间只允许一次续期；新凭据成套替换，避免两个请求把彼此的票据作废。认证确已失效时尝试平台允许的续期，失败再提示重新连接；权限不足、网络失败、限流要分开处理，不能无限重登。
  6. 手机调度：进入 App、手动刷新时查询；后台用系统允许的机会更新。小组件优先读共享的额度快照，避免它与主 App 同时抢着续期。后台执行时间由 iOS 决定，Keychain 本身不会自动拉取额度。Apple 后台策略。

为什么不能把 91 项都写成“网页登录即可”

  • 有些直接使用访问密钥：如 OpenRouter、ElevenLabs、DeepSeek 余额，以及多种网关。密钥 + Keychain + 网络查询更直接，额度范围由密钥权限决定。
  • 有些依赖网页会话：如 Cursor、Manus、Notion 的现有网页路线。可以设计手机内网页登录试验，但必须验证第三方登录、会话保存、组织选择及有效期，不能把桌面 Chrome 导入直接改名成手机登录。
  • 有些还有额外绑定：Grok 当前网页账单接口除了 Cookie 还要求浏览器 WKE 密钥；Venice 的短会话需要活跃网页续期；Windsurf 需要 localStorage 会话包。这些都不是保存一条 Cookie 后定时请求就够了。
  • 有些来自电脑本地：JetBrains AI 的 IDE 信息、Pi 的本地用量、llmman 的模型内存等，并不因增加网页登录而获得远程额度接口。独立手机路线需要其他获准数据源，否则只能做电脑配套查询，或不接入该项。

因此采用共用一个凭据保管与更新框架，各平台选择自己的接入办法。下表新增的最后一列按“接入判断 → 登录 → 保存 → 续期 → 查额 → 待验证点”逐项填写。标为“密钥路径可迁移”表示源码有可抽取的网络路线，不表示已经真机验证；“网页会话需验证”也不是断言该平台不能做。

先验证登录闭环，再决定首版支持名单。每个候选平台至少覆盖：Apple/邮箱/其他实际登录方式、取消登录、同平台多账户、工作区切换、关闭网页后的刷新、凭据过期与撤销、锁屏/重启、退出后的清理。涉及内部接口或需要平台应用注册时，还需确认我们的发布版本有相应使用权限。

复用时最容易踩的坑

  1. 把 91 个入口当成 91 种订阅。OpenAI API 与 Codex 订阅、Moonshot API 与 Kimi 套餐、xAI API 与 Grok，都是不同账本。名称同公司不等于权限和额度相通。
  2. 只抄 README。本版有过时摘要：Ollama 已出现月度积分结构；Doubao 多了 arkcli/AK-SK 套餐查询；DeepSeek 也有网页登录明细。StepFun 保存密码与通用隐私口号冲突。看具体实现和平台返回字段。
  3. 把内部查询地址当成长期公开接口。网页接口、页面结构、浏览器会话绑定、验证码或授权策略改变，都可能令功能失效。平台多意味着持续维护面大。
  4. 只完成首次登录，不测试过期续期。共享同一份 refresh token 给多个设备各自刷新，可能相互挤掉登录。要测试到期、撤销、重登、切换工作区和多端同时查询。某些登录动作也有副作用：Gemini 登录切换会先清除已有 CLI 登录文件，不能把整个项目的登录行为一概视为只读。
  5. 把同一邮箱当成同一账户范围。一个用户可有个人和公司工作区，Apple 隐藏邮箱也不适合作唯一标识。按平台稳定用户 ID 和工作区 ID 区分；旧请求不能覆盖新账户。
  6. 把缓存当成最新结果。项目保留某些暂时网络失败前的结果及原时间。手机应清楚显示“上次更新”“待重新登录”“暂时不可用”，不能把旧数据换上当前时间。
  7. 混算费用和剩余额度。本地日志 × 模型价表是估算，不是会员实际扣款；一台电脑的历史也不等于全账户历史。币种、积分和请求数不能放在一个总额里直接相加。
  8. 以为刷新绝不消耗额度。Doubao 的 API-key 探测会发出 max_tokens:1 的模型请求；Azure OpenAI 也用最小请求确认连接。AWS Cost Explorer 查询本身另有收费，一次刷新可能包含多次查询。需要逐项识别、低频执行，并在产品中说明。其他正常查账接口不能因此被一概说成会收费。AWS 查询计费说明。
  9. 照搬桌面秘密保存与同步默认值。配置 JSON 中确有秘密字段；文件权限不等于加密。iCloud 总开关默认关，但“包含秘密”子开关默认开，启用时可能上传对应字段到 CloudKit 的加密字段。手机版应把秘密同步作为明确设计决策。
  10. 承诺手机每分钟后台准时刷新。普通 iOS 后台刷新时间由系统决定，不能保证桌面式常驻轮询。以打开 App 时更新、显示时间戳为基础；通知另行设计。Apple 后台执行说明。
  11. 直接沿用上游应用身份和插件安装方式。Copilot 当前借用的应用标识、Gemini 的 CLI 授权参数、上游 CloudKit 容器及签名配置，都不是新 App 自己的配置。随包解析脚本与运行时安装新功能也需分开；不能据此保证 App Store 接受任意插件。
  12. 把开源许可等同平台授权。项目是 MIT，允许修改、分发和商业使用，但要保留版权和许可通知；依赖许可与品牌另查。这不替你取得各服务商账户接口的使用许可。项目 LICENSE、MIT 原文。
