CodexBar 功能与 iOS 复用研究

研究日期：2026 年 10 月 10 日 · 已增补手机登录与钥匙串方案 · 本地版本：0.73.1（166） · 提交：03a51bdcfc6f6804e005d7e5007de67bac82b494

CodexBar 很适合当作“各平台额度接入的参考库”，但不能直接打包成 iPhone App。值得借用的是平台请求、数据解释、账户隔离和错误处理；最需要重新设计的是登录、凭据保存、手机后台刷新，以及第三方服务对你这个新 App 的授权。

可以把它想成一个“替你向很多商家查会员余额的管家”。每家商店的会员卡、查账窗口和账单格式都不同，它为每家准备了一套办法，再把结果整理成你看得懂的进度条。

本报告依据本地源码、测试用例和项目文档整理；iOS 规则和少数影响判断的平台变更另查官方资料。91 项表示这个版本登记的接入入口，不表示 91 家公司、91 种订阅，也不表示已经用 91 个真实账户逐一验证可用。本文没有读取你的真实登录凭据、启动登录或执行真实额度查询。

它能做什么

主产品是 macOS 菜单栏应用：看各平台用量、恢复时间、余额和告警；还有使用历史、费用图表、多账户管理和桌面小组件。仓库也提供 macOS/Linux 命令行程序，以及调用这个程序的 Linux 桌面界面。它不是现成的 iOS 工程。

 | 显示内容
 | 大白话解释
 | 需要注意

 | 订阅额度
 | 会员包里的本轮、每周或每月额度用了多少，什么时候恢复。
 | 一个账户可能同时被好几条限额约束；不是把几条剩余额度相加。

 | 充值余额与积分
 | 钱包还有多少钱，或还有多少平台积分。
 | 金额、积分、字符数、token 不是同一种单位。

 | 账单与预算
 | 这个月花了多少，离自己或团队设定的预算还有多远。
 | 团队总池和你的个人上限要分开；预算不一定是硬性停用额度。

 | 本机用量与费用估算
 | 翻电脑上的使用记录，统计用了哪些模型，再按价格表估一个金额。
 | 不等于真实扣款，也通常看不到其他电脑上的全部使用。

 | 辅助状态
 | 平台是否故障、工具是否能连接、本地模型占多少内存。

登录是怎么切进去的

先把“你用什么方式证明自己是谁”和“软件拿什么凭据查额度”分开。Apple ID、Google、邮箱密码，是进入服务商账户的方法；登录成功后的 token、Cookie 或 API key，则像服务商发出的通行证。CodexBar 大多数时候接手的是通行证，不是 Apple 密码或邮箱密码。

用户在平台官方页面登录
Apple／邮箱／其他方式→平台给官方工具或浏览器发通行证→CodexBar 取得已有通行证→带通行证查额度

这意味着：同一个平台账户，只要官方登录后给出了项目支持的凭据形式，最初用 Apple 还是邮箱通常不会改变查额度的基本逻辑。具体登录选项仍由平台决定。不要把“给我们的 App 加一个使用 Apple 登录按钮”误认为能自动获得用户的 OpenAI、Claude 或其他平台账户授权。

 | 路径
 | 项目怎么做
 | 搬到手机时的含义

 | 借用官方电脑工具
 | Codex、Claude、Gemini 等从电脑工具留下的文件或钥匙串中取凭据；必要时启动该工具登录。
 | iPhone 没有这些电脑目录和命令行工具，需要重新建立授权流程。

 | 设备验证码授权
 | Copilot 展示验证码、打开 GitHub 官网，让用户在那里确认；程序等待授权完成。
 | 交互可以借鉴，但要确认自己的应用身份能获得查询 Copilot 额度的权限。

 | 借用网页登录状态
 | Cursor、Manus、Notion 等读取特定网站的 Cookie 或浏览器存储；也提供手动导入。
 | 不能直接读取 iPhone Safari 或其他 App 的私人登录数据。自有网页登录也不保证获得可长期使用的查额凭据。

 | 用户提供访问密钥
 | DeepSeek、OpenRouter、ElevenLabs 等带用户密钥请求平台接口。
 | 网络请求通常较好迁移，但密钥权限、可查询数据和保存方式仍要逐项确认。

 | 直接用户名密码
 | StepFun 是明确例外：项目自己提交用户名密码，换取会话凭据。
 | 不要把这种做法推广到所有平台；现有密码保存方式也需要重做。

Codex 的完整例子

• 用户点登录后，项目启动官方 codex login，由官方工具完成浏览器登录。CodexBar 本地没有自己实现一整套 Apple 登录、PKCE 或网页登录回调。

• 官方工具留下 auth.json。里面可能包含访问凭据、续期凭据、账户标识、过期时间。CodexBar 按指定账户目录读取。

• 自动模式按 PAT → OAuth → CLI 尝试可用路径；指定工作区时会限制不带工作区范围的 CLI 回退，避免查错账户。

• OAuth 路径带访问凭据和账户标识，查询 chatgpt.com/backend-api/wham/usage。返回结果再整理为短周期、周限额、余额等。网页附加明细是另一条来源，不是有一个 token 就自然有所有账单。

• 凭据过期时，当前额度读取路径刻意不自行兑换共享的续期凭据。原生凭据在允许时交官方 CLI 恢复；外部凭据需回所属工具重新登录，指定工作区时也可能禁止 CLI 回退，不能保证自动续期。这是为了避免“手机和电脑同时续期，把对方手中的票据弄作废”。源码有刷新辅助类，不代表当前读取路径正在调用它。

• 多个 Codex 账户使用分别管理的目录，并核对用户和工作区。网页 Cookie、缓存和额度也要跟着账户分隔，不能只看显示邮箱就拼到一起。

代码：CLILoginRunner.swift:31；CodexProviderDescriptor.swift:150、465；CodexOAuth/CodexOAuthCredentials.swift:97；CodexOAuth/CodexOAuthUsageFetcher.swift:379；ManagedCodexAccountService.swift:43。

PAT 是另一种工作区访问凭据，不能当作普通 OpenAI API key。项目先查询它属于谁，再查询那个账户的额度。截至本次核验，官方文档将 Codex 访问令牌支持范围列为 ChatGPT Business 和 Enterprise，因此不能把这条路径当成面向所有 Plus/Pro 用户的手机登录方案。官方访问令牌说明。

当前官方也已有 Sign in with ChatGPT 的相关集成文档：开源、本地应用有对应的计划使用授权流程，付费或远程托管场景另有申请渠道。这是新 App 可以调查的方向；这些文档本身没有证明我们的额度监控 App 已获得读取该内部额度接口的权限，不能直接套用官方工具的应用标识。官方集成范围、客户端申请说明。

其他平台的关键差异

• Claude：区分官方工具凭据、手工 token、网页 Cookie 和管理 API key；这些能读到的内容不同。项目还记录“谁负责续期”，避免几个程序抢着换同一张票据。管理 API 的费用不等于个人订阅剩余额度。

• Copilot：设备授权流程目前使用 VS Code 的应用标识。复制这段代码能发出请求，不代表新 App 可继续使用这个身份，也不代表自己的 GitHub 授权天然能读内部额度接口。

• Gemini：读取已安装 Gemini CLI 的凭据，还会从其安装文件解析授权参数。不能原样搬到手机；个人、AI Pro、Ultra 的旧 CLI 登录路线还有迁移变化。

• Cursor：既能借浏览器会话，也会读取电脑上 Cursor 自己的数据库。它不是只打开一个登录网页，就能在任意系统拿到同样数据。

• StepFun：源码把用户名放入统一配置的 apiKey 字段，把密码放入 cookieHeader 字段。这个版本确实存在保存密码的路径，不能直接复述 README 的“不会保存密码”。

保存凭据也不是“全部存在钥匙串”。手动密钥、部分 token 和账户列表存在配置 JSON，依靠仅本人可读写的文件权限；部分自动 Cookie/OAuth 缓存使用钥匙串。对 iOS 新项目，建议普通数据库只保存“钥匙在哪里”的引用，真正的密钥放系统 Keychain。Apple Keychain 说明。

版本来自 Package.swift 与 Package.resolved；插件引擎选择见 ProviderPluginRuntime.swift:323。并非 React、Flutter 或 Electron 主应用。

它可以拆成四个角色：

• 平台通讯录：记住每个平台叫什么、显示哪些栏目、支持哪些查询方法。

• 各平台办事员：分别处理请求、网页登录状态、官方工具输出或本地文件；某条路不可用时，只按允许的规则换另一条。

• 总账本：保存最新结果、来源、账号和错误状态；防止换了账户后，旧请求又把前一个人的数据填回来。

• 展示窗口：同一份结果用在菜单栏、设置、图表、小组件或命令行输出。

定时／用户点刷新→选择平台与账户→取得对应凭据
选择可用查询路径→请求平台或读本机记录→整理成统一额度记录→核对账户和时效
保存并显示

例如 A 平台说“已用 30%”，B 平台说“剩余 0.7”，C 平台给一段终端文字；各自的办事员先翻译成统一格式，界面就不必懂 91 种说法。实际网络和本地来源是分别实现的，并不存在一个能向所有平台查询订阅额度的万能接口。

当前架构也不是一套必须经过作者服务器的云服务：主要查询在用户设备进行。可选 CloudKit 同步和可选 HTTP 服务另算。新增平台的成本主要在“拿到正确凭据、看懂平台回答、处理失效”，画新卡片反而较简单。

查询结果 ProviderFetchResult
├─ 数据来源：OAuth / 网页 / API key / 电脑工具 / 本地记录
├─ 采用的查询方法、诊断信息
├─ 额度快照 UsageSnapshot
│  ├─ 第一、第二、第三条额度（可以缺席）

│  ├─ 更新时间
│  └─ 数据可信程度：精确 / 估算 / 只有百分比 / 未知

一条额度 RateWindow
├─ 已用比例：35%（示例）
├─ 周期长度：300 分钟（示例；也可能未知）
├─ 恢复时间：平台返回的时间（可能没有）
├─ 下次逐步恢复多少（可选）
└─ 是否只是占位，不能当成真实零用量

钱包／预算记录
├─ 已用、上限、剩余余额
├─ 单位／币种：USD、CNY 或平台积分等
├─ 个人额度还是团队共享池
└─ 余额是否真的读取成功、分别在什么时候取得

“没有查到”一定要跟“剩余为零”分开。例如平台只告诉你恢复时间，却没给剩余比例，就不能画一个“额度用完”的红条。五小时额度还很多而周额度已满时，也不能简单取平均告诉用户“还有一半可用”。

还有一个特别容易被复用者忽略的历史包袱：同一个“百分比”字段，不总是在讲额度。LLM Proxy 有些窗口用它承载计数占位；DeepInfra 有时用 0/100 表示余额状态；Zed 有账期已经过了多少的时间进度；llmman 则是内存占用。手机不能不加区分就给所有平台画“剩余额度”条，应另加“指标类型、单位、账户范围、是否真实测量”这些说明。

实现例子：Resources/Plugins/llmproxy.ts:123、deepinfra.js:73、zed.js:141、llmman.ts:93。

新 iOS App 可以保留这个思路，但建议把凭据单独存放：

账户目录：平台 ID + 平台用户 ID + 工作区 ID + 显示名称 + 凭据引用
系统钥匙串：访问凭据 + 续期凭据 + 到期时间 + 由哪个设备负责续期
额度记录：账户目录 ID + 指标/单位 + 查询结果 + 来源 + 取得时间 + 错误状态
历史记录：只存必要的额度变化；不混入可登录账户的秘密

适合怎样借用到 iOS

最值得借的是“按平台分开接入、统一整理结果”的骨架。核心库还混有启动电脑程序、读浏览器目录、扫描进程等代码，因此不是给新 iOS 工程勾选一个依赖就能运行的现成 SDK。需要把这些桌面能力从纯网络与解析代码中拆出来。

 | 复用判断
 | 具体内容

 | 优先抽取
 | 数据格式、比例与时间解释、平台返回结果解析、账户和工作区隔离、查询失败分类、测试样本。对于可获授权的接口，抽取网络请求逻辑。

 | 调整后使用
 | 刷新调度、图表、历史保存、小组件、插件运行环境；统一额度模型也应减少当前大量平台专用字段。

 | 需要重做
 | 首次登录、续期责任、Keychain 保存、退出清理、iOS 页面、后台策略、自己的应用标识、CloudKit 容器和发布配置。

 | 不能原样搬运
 | 读取其他 App 私人文件或钥匙串、导入电脑浏览器 Cookie、运行 Codex/Claude CLI、扫描桌面进程、Mac 菜单栏及 Sparkle 更新。

苹果对 iOS App 做了隔离：一个 App 不能随意读取另一个 App 的私人文件，只能走系统明确提供的渠道。因此“用户手机已装 ChatGPT 且已登录”，不代表我们的 App 能拿到它的登录状态。Apple 应用隔离说明。

有正式授权回调的平台，可以考虑系统网页登录组件 ASWebAuthenticationSession。它像“陪用户去官方柜台办授权，再拿回官方交给本 App 的回执”，不是让 App 偷看 Safari 的 Cookie。Apple 网页授权组件。

 | 产品路线
 | 优点
 | 代价与适用情况

 | 手机直接连接平台
 | 不要求电脑在线；密钥可以留在用户手机。
 | 适合明确开放访问密钥或授权接口的平台。首版平台数量应服从真实接入能力，不能先承诺 91 个。

 | 手机 + 用户电脑采集端
 | 电脑继续利用已有登录状态，手机只看同步后的额度；复用范围通常更大。
 | 电脑需要运行；离线时只能显示最后一次结果。必须做配对、加密传输和断连提示，不适合作为“完全独立手机 App”的无条件替代。

 | 自己的服务器集中查询
 | 便于集中调度、发送变化通知。
 | 要处理所有用户的凭据和隔离、费用、风控与服务授权；服务器也不能凭空解决没有查询权限的问题。

仓库已有可复用的“电脑给手机提供结果”基础。codexbar dashboard 能输出统一结果；codexbar serve 提供 /dashboard/v1/snapshot，包括平台、账户、额度、更新时间和错误。它不是现成手机服务：默认只监听本机，传输是普通 HTTP；跨设备使用需配对、身份校验和加密通道。现有 Dashboard 接口说明。

我的建议是先以独立手机使用为首版目标，挑出能明确授权、可长期续期的入口；把 Codex、Claude、Copilot、Cursor 作为单独的登录可行性验证。若这些订阅平台是产品不可缺少的核心，而纯手机授权无法成立，再决定是否接受电脑采集端。

新增研究：网页登录 + iPhone 钥匙串，能否统一采用？

可以采用“凭据保存在 iPhone Keychain、手机直接查询”的基础设计；不能把同一种网页登录流程套到全部 91 个入口。钥匙串负责保管已经拿到的通行证，平台决定是否发证、允许查什么、如何续期。界面上看起来都是“打开网页”，内部可能是不同的流程。

本节按你描述的竞品交互评估技术可行性，没有确认竞品的私有实现。仅凭“弹出网页、登录后保存到钥匙串”，无法判定它使用正式授权回调、自己的网页会话，还是其他平台专用方式。下面的手机方案属于基于源码的改造设计，尚未在真机和真实账户上验证。

三种“打开网页”，不能混为一谈

 | 做法
 | App 实际能拿到什么
 | 适用判断

 | 系统授权窗口
ASWebAuthenticationSession
 | 平台通过约定回调地址返回授权结果；标准授权码流程再由 App 换取访问凭据。不是导出浏览器全部 Cookie。
 | 优先采用。需要平台接受我们自己的应用身份、回调地址和所需权限，并明确允许查询额度。支持网页登录不等于支持这组权限。

 | App 自己的网页窗口
WKWebView
 | 可通过 WKHTTPCookieStore 管理这个窗口自己的 Cookie；有的网站还把会话放在 localStorage，需单独适配。
 | 部分网页型平台的候选路线。必须验证登录可完成、取得的会话能查询、失效后能恢复。它不是 Safari，也拿不到其他 App 的私人会话。

 | 普通 Safari 页面
Safari / SFSafariViewController
 | 用户可以浏览和登录；App 不能因页面打开了，就读取其中的网页数据。
 | 仅打开页面不够。仍需要平台回调、设备验证码流程，或用户在官方控制台生成密钥后明确交给 App。

依据：Apple 系统网页授权、Safari 页面隔离、WebKit Cookie 管理。

WKWebView 不能当作绕过平台授权限制的万能办法。有些登录提供商明确不允许在 App 可控制的内嵌网页中完成 OAuth；例如 Google 有这项限制。即使某网站邮箱登录能成功，Apple、Google、企业 SSO 的跳转也需要分别验证。遇到禁止或风控时，应使用平台支持的外部授权流程，不能靠伪装浏览器保证接入。Google OAuth 政策。

Cookie 上的 HttpOnly 表示不能交给网页 JavaScript，不表示 App 自己网页窗口的原生 Cookie 管理接口只能忽略它。应使用原生 Cookie store 并保持这些限制，不用 document.cookie 作为完整会话来源。Cookie 也不一定是全部：设备密钥、反跨站请求标记、组织 ID 或 localStorage 会话包可能同样必要。Apple HttpOnly 说明。

建议采用的手机实现

按平台选入口
正式网页授权／访问密钥／经验证的网页会话→取得本 App 可用的凭据
核对账户、地区和工作区→秘密进 Keychain
普通配置只保存引用→按该平台规则续期
不能续期时请用户重登→请求额度并存快照
界面和小组件显示更新时间

• 正式授权：为我们的 App 申请平台支持的客户端身份，用系统网页授权窗口；标准原生 OAuth 采用授权码与 PKCE，验证回调及 state。它像“只有本次申请的人能兑换的取票码”。不能把桌面官方工具的身份或固定回调直接当作我们的身份，也不能把可保密的服务端密钥硬塞进 App。原生应用 OAuth 标准。

• 访问密钥：打开官方密钥管理页供用户创建，再由用户明确粘贴到 App；保存在 Keychain，选择最小可用权限。它不一定有“刷新令牌”，被撤销或到期通常由用户换新密钥。不能把 API 钱包当成个人会员额度。

• 网页会话：在平台允许且实测可行的前提下，用独立 WKWebView 登录；只提取该平台查询必需的会话，验证账户后保存。恢复 Cookie 时保留域、路径、安全标记和有效期；只发往对应平台允许的地址。localStorage、短期令牌、设备密钥须按平台单独处理。不能宣称把一个 Cookie 字符串写进 Keychain 就解决了登录。

• 凭据保管：以“平台 + 地区/服务器 + 稳定账户标识 + 工作区”隔离；OAuth 保存访问/续期凭据及到期时间，密钥路线保存 key，网页路线保存必要会话与绑定信息。普通配置与日志不存这些原文。这里的 Keychain 是 App 使用的系统秘密存储，不是让 App 读取用户“密码”应用中的所有账户。

• 额度更新：用 URLSession 抽取并调用已有查询逻辑。每个账户同一时间只允许一次续期；新凭据成套替换，避免两个请求把彼此的票据作废。认证确已失效时尝试平台允许的续期，失败再提示重新连接；权限不足、网络失败、限流要分开处理，不能无限重登。

• 手机调度：进入 App、手动刷新时查询；后台用系统允许的机会更新。小组件优先读共享的额度快照，避免它与主 App 同时抢着续期。后台执行时间由 iOS 决定，Keychain 本身不会自动拉取额度。Apple 后台策略。

这三家值得做独立手机原型验证。源码不仅有电脑工具来源，也有实际的网页会话查询逻辑。手机需要补齐的是“在自己的网页窗口中取得可用会话，并在过期后恢复”，下列请求路径是可参考的连接点，不是手机已经验证成功的结论。

 | 平台
 | 候选手机路线
 | 还需验证什么

“存在钥匙串”还需要做出的三个技术选择

 | 选择
 | 建议及实际影响

 | 锁屏后能否读取
 | 如果只在前台查，可用 kSecAttrAccessibleWhenUnlockedThisDeviceOnly。若需要锁屏后台查询，评估 kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly：重启后用户至少解锁一次才可读取，之后可供后台使用。每次读取都要求 Face ID 会与无人操作的后台刷新冲突；并非钥匙串失败。

 | 是否跨设备同步
 | 建议首版先不自动同步可续期会话，使用本设备保存。ThisDeviceOnly 与可同步的 Keychain 项不能组合；如以后支持 iCloud，同步配置/快照与同步登录凭据须分开设计，还需处理多个设备争抢续期的问题。

 | 网页数据是否另存一份
 | WKWebView 默认会把网页数据持久写入自己的数据区。若产品承诺“登录凭据只持久保存在 Keychain”，需使用不持久的 WKWebsiteDataStore.nonPersistent()，并明确控制必要凭据的保存与恢复。依赖不可导出设备密钥或完整网页环境的平台未必兼容；如果必须使用持久网页资料，应如实披露并在退出时清理，不能仍宣称只存钥匙串。网络查询层也要按账户使用独立的 URLSessionConfiguration.ephemeral 或等效不落盘配置，避免共享 Cookie、认证缓存和磁盘缓存再次保存秘密；仅改网页窗口还不够。

依据：Keychain 访问条件、后台可访问的本设备项、iCloud 同步属性、WebKit 数据保存方式、临时网络会话、网络 Cookie 存储。以上推荐设置是针对本产品的设计建议，不是声称 CodexBar 已实现这些 iOS 行为。

退出账户时，要清理 Keychain 对应项、该账户的网页会话、本地额度缓存和小组件快照；平台提供撤销接口时也应撤销授权。不要只删除屏幕上的账户卡片。网页登录关闭后是否还可查、App 被关闭或手机重启后能否恢复，也是验收项目。

为什么不能把 91 项都写成“网页登录即可”

• 有些直接使用访问密钥：如 OpenRouter、ElevenLabs、DeepSeek 余额，以及多种网关。密钥 + Keychain + 网络查询更直接，额度范围由密钥权限决定。

• 有些依赖网页会话：如 Cursor、Manus、Notion 的现有网页路线。可以设计手机内网页登录试验，但必须验证第三方登录、会话保存、组织选择及有效期，不能把桌面 Chrome 导入直接改名成手机登录。

• 有些还有额外绑定：Grok 当前网页账单接口除了 Cookie 还要求浏览器 WKE 密钥；Venice 的短会话需要活跃网页续期；Windsurf 需要 localStorage 会话包。这些都不是保存一条 Cookie 后定时请求就够了。

• 有些来自电脑本地：JetBrains AI 的 IDE 信息、Pi 的本地用量、llmman 的模型内存等，并不因增加网页登录而获得远程额度接口。独立手机路线需要其他获准数据源，否则只能做电脑配套查询，或不接入该项。

因此采用共用一个凭据保管与更新框架，各平台选择自己的接入办法。下表新增的最后一列按“接入判断 → 登录 → 保存 → 续期 → 查额 → 待验证点”逐项填写。标为“密钥路径可迁移”表示源码有可抽取的网络路线，不表示已经真机验证；“网页会话需验证”也不是断言该平台不能做。

先验证登录闭环，再决定首版支持名单。每个候选平台至少覆盖：Apple/邮箱/其他实际登录方式、取消登录、同平台多账户、工作区切换、关闭网页后的刷新、凭据过期与撤销、锁屏/重启、退出后的清理。涉及内部接口或需要平台应用注册时，还需确认我们的发布版本有相应使用权限。

复用时最容易踩的坑

• 把 91 个入口当成 91 种订阅。OpenAI API 与 Codex 订阅、Moonshot API 与 Kimi 套餐、xAI API 与 Grok，都是不同账本。名称同公司不等于权限和额度相通。

• 只抄 README。本版有过时摘要：Ollama 已出现月度积分结构；Doubao 多了 arkcli/AK-SK 套餐查询；DeepSeek 也有网页登录明细。StepFun 保存密码与通用隐私口号冲突。看具体实现和平台返回字段。

• 把内部查询地址当成长期公开接口。网页接口、页面结构、浏览器会话绑定、验证码或授权策略改变，都可能令功能失效。平台多意味着持续维护面大。

• 只完成首次登录，不测试过期续期。共享同一份 refresh token 给多个设备各自刷新，可能相互挤掉登录。要测试到期、撤销、重登、切换工作区和多端同时查询。某些登录动作也有副作用：Gemini 登录切换会先清除已有 CLI 登录文件，不能把整个项目的登录行为一概视为只读。

• 把同一邮箱当成同一账户范围。一个用户可有个人和公司工作区，Apple 隐藏邮箱也不适合作唯一标识。按平台稳定用户 ID 和工作区 ID 区分；旧请求不能覆盖新账户。

• 把缓存当成最新结果。项目保留某些暂时网络失败前的结果及原时间。手机应清楚显示“上次更新”“待重新登录”“暂时不可用”，不能把旧数据换上当前时间。

• 混算费用和剩余额度。本地日志 × 模型价表是估算，不是会员实际扣款；一台电脑的历史也不等于全账户历史。币种、积分和请求数不能放在一个总额里直接相加。

• 以为刷新绝不消耗额度。Doubao 的 API-key 探测会发出 max_tokens:1 的模型请求；Azure OpenAI 也用最小请求确认连接。AWS Cost Explorer 查询本身另有收费，一次刷新可能包含多次查询。需要逐项识别、低频执行，并在产品中说明。其他正常查账接口不能因此被一概说成会收费。AWS 查询计费说明。

• 照搬桌面秘密保存与同步默认值。配置 JSON 中确有秘密字段；文件权限不等于加密。iCloud 总开关默认关，但“包含秘密”子开关默认开，启用时可能上传对应字段到 CloudKit 的加密字段。手机版应把秘密同步作为明确设计决策。

• 承诺手机每分钟后台准时刷新。普通 iOS 后台刷新时间由系统决定，不能保证桌面式常驻轮询。以打开 App 时更新、显示时间戳为基础；通知另行设计。Apple 后台执行说明。

• 直接沿用上游应用身份和插件安装方式。Copilot 当前借用的应用标识、Gemini 的 CLI 授权参数、上游 CloudKit 容器及签名配置，都不是新 App 自己的配置。随包解析脚本与运行时安装新功能也需分开；不能据此保证 App Store 接受任意插件。

• 把开源许可等同平台授权。项目是 MIT，允许修改、分发和商业使用，但要保留版权和许可通知；依赖许可与品牌另查。这不替你取得各服务商账户接口的使用许可。项目 LICENSE、MIT 原文。

针对发布，Apple 的规则还涉及第三方服务授权（5.2.2）、动态代码（2.5.2 / 4.7）和用户主账户登录（4.8）。连接一个服务账户与建立你 App 自己的主账户是不同场景，不能笼统说“出现第三方登录就一定必须加 Apple 登录”。这里是需要按最终产品核对的边界，不是已获得上架保证。App 审核指南。
