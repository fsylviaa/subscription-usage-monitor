# 任务执行与验收约定

确认日期：2026-10-10。适用于本文件夹全部任务。本文规定如何执行任务，不表示已建立 App 工程或通过功能验收。

## 1. 本次交付边界

- 终点：通过 Xcode 安装到用户自己的 iPhone，能够自用，并完成真机验收。
- 只规划开发及上述验收；不规划 TestFlight、测试分发、商店材料、上架准备、提交审核或正式发布。技术研究中的公开发布资格、全系统版本测试矩阵不自动成为本清单任务。
- 设计阶段已结束。现有 Figma 固定为只读的视觉、文案和交互参考，此后不修改、不重建、不安排重新验收原型。冲突时按用户最新决定和需求 0.8；后续细调在 App 中做。
- 仅 Codex 订阅与同平台多账户。保留公共能力和 Codex 接入的简单分离，不提前建设 13 平台、后端、工作区管理、配置选择器或额外调试产品页面。
- 手机直接登录并查询是真实开发任务。现有参考项目不等于手机已实现；遇到确实无法满足需求的事实，记录缺口再讨论，不自行加电脑辅助、API 余额或其他替代功能。
- 工程配置只处理本项目在目标手机上构建运行所需部分；已有配置复用，不为签名或最低系统版本另建研究/发布阶段。

## 2. 任务大小与执行顺序

1. 按总览 T01 → T56 的编号顺序执行；每次只完成一个文件描述的成果。直接依赖表示必须先有的能力；编号中较早但未列为依赖的项不自动成为技术前置。
2. 每个任务的实现工作应能在一次对话、一个小提交中完成。任务中实现与相应测试一起交付；不在同一任务里顺手做后续功能。
3. 真机系统调度、真实重置和自然授权到期可能需要经过实际时间。开发者从 T14、T30、T39 起保存去敏观察结果，在 T52–T54 的独立验收任务中核对；不要求对话一直等待，也不把等待另建成开发阶段。
4. 缺少某项真实结果时如实标“待验”，不能以模拟结果替代或写成已完成。自然观察任务具备所需证据后，可在一次会话核验并提交；尚无证据则该项保持待验。
5. 若实际任务超过一个明确成果，应先在本文件夹拆出小任务并更新索引与依赖，然后继续；不擅自扩大产品范围。
6. 发现问题时就地修复与该任务直接相关的问题。验收阶段若发现跨模块缺陷，将缺陷按单一结果拆成修复任务、更新依赖并各自存档，不把“全量验收”变成无限大的修改任务。

## 3. 给项目经理的验收方式

- 每份任务先写“本次交付”和“你怎么验收”，开发细节放后面。
- 页面任务：提供可运行版本、入口、操作、预期结果。用户不需要读代码、网络报文或日志。
- 基础能力尚无页面时：开发者运行固定输入的测试，展示易读的“输入／操作 → 实际结果 → 是否通过”表及运行结果。验收不是凭开发者一句“已完成”。后续真机任务仍验证实际体验。
- 难稳定复现的 49/50/51 分、过期、部分失败、迟到响应等，由开发者在隔离测试环境准备，不要求用户制造网络故障或修改代码；任务写明测试构建与真实平台结果的区别。
- 测试数据与真实账户、共享组件数据隔离，不覆盖真实成功快照。产品中不加入演示模式、故障选择器或调试入口；测试脚手架不作为交付给日常用户的功能。
- 通知逻辑可用虚拟通知中心测试。模拟额度、模拟时间不得向系统发送真实通知。实际锁屏通知必须依据真实账户提供的有效重置时间验收。
- 组件画面刷新、后台执行和系统通知遵守 iOS 调度。开发者记录请求与实际发生的时间，区分“已请求”“调试触发”“自然执行”；不以严格 30 分钟或瞬时换图为通过标准。
- 至少两个真实 Codex 账户用于真实多账户验收；用户本人完成账户密码/验证码等私密操作。条件未具备时标待验，不把测试账户当真实账户，不为验收开户或购买订阅。

## 4. 每个任务的完成与 Git 存档

Git 仓库：`/Users/iceflying/codex/订阅用量监控/app`。参考项目有自己的仓库，不在其中提交本 App 的改动。

每个任务都执行：

1. 开始前检查当前变更和前置任务的验收/提交记录，保护其他任务或用户尚未提交的工作。
2. 完成本任务功能和必要自检。在 `记录/Txx-验收.md` 填写实际结果；更新任务文档的状态。没有执行的步骤明确标待验。
3. 检查差异及新增文件，只暂存本任务实际改动与对应验收记录。不得提交授权、密码、真实令牌、签名秘密或不相关文件；不使用盲目的全仓库暂存。
4. 用一次小提交建立存档点，提交信息包含任务编号和结果，例如 `feat(T17): 保存账户排序`；纯验收可用 `test(T51): 记录两尺寸组件真机验收`。若任务只产出验收记录，该记录本身就是可提交成果。
5. 提交后确认产生提交号并检查剩余变更，向用户报告“做了什么、怎么验收、验收结果、Git 提交号”。未完成的部分可以保存进行中提交，但不能标任务完成。

**完成判定：本任务范围内成果存在、所列验收实际通过、结果有记录、Git 存档成功。** 用户亲自验收状态另列；开发者不得冒称用户已验收，也不新增每个任务都必须等待用户回复才继续的流程。

验收记录随成果提交，不填写该次提交自己的哈希；用任务编号在 Git 历史查找，提交后在交付回复报告实际哈希，避免自引用造成持续修改。用户未明确要求时不推送远端。
